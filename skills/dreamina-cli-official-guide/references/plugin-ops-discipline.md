# 插件源码改动的运维纪律（video-assets）

改 `src/*.js`、跑自检、判「是否生效」、做回滚点时的可复用纪律。均来自实测教训，不是推测。

## 1. 改动前先备份，备份点按内容核验

- 插件目录**不是 git 仓库**，只能目录快照回滚：改 `src/*.js` 前先整目录备份。
- 同日多次改动要按日期续号；**续号会重名**，先列出已有备份目录再定新名。
- **备份点按内容核验，不按名字核验**：回滚点必须逐文件哈希核对（至少关键 `src/*.js`），并写明该点含/不含哪些改动。实测教训：一处备份被标注「P2 未改」，哈希比对后实际已含 P2 代码——按标签回滚等于没回滚。只有备份目录内留了 `BACKUP-MANIFEST-*.txt` 的点，事后才可自证。

## 2. 「是否生效」要分两级判，不要拿时间顺序当结论

- 网关**不热加载**插件源码，必须重启才生效；且**网关重启在当前 agent turn 结束后才落地**，turn 内轮询进程会误判「没重启」。
- 一级（弱）：网关 `node` 进程 CreationDate 晚于 `src/*.js` LastWriteTime——只能排除「明显是旧进程」，**不等于该进程加载的就是当前哈希**（热加载、多进程、启动后替换都能让两条同时成立却不一致）。
- 二级（可交付）：二选一坐实——① **功能探测**：挑一条真正走被改分支的零成本调用（如 `video_canvas_dreamina_cli_plan` + `execute=false`，或看被修门禁的 `blockers` 文案是否变化）；② **模块指纹**：让插件启动时把源码 SHA256 打进日志，再与磁盘哈希对照。
- 两者都做不到时，交付里如实写「运行态是否已加载未证明」。
- **「调用结果正常」同样不足以证明已加载新代码**：若测试场景本就不触及被改分支，修复前后结果会完全一致；此时标注该验证边界，不要把无差异的真实调用当修复证据。

## 3. 文档漂移自查

改动落地后用新引入的标记（新函数名、新工具名、新模型值）grep `README.md`，命中 0 即为漂移，必须补齐——插件 README 是下游 Agent 判断操作顺序的唯一文档面。

## 4. 新增内容的「三处同步」清单

- 新增**工具**：`src/index.js` 注册、`openclaw.plugin.json` 的 `contracts.tools`、`TOOL_TITLES_ZH`/`TOOL_DESCRIPTIONS_ZH` 标签映射——缺一处 `check:preflight` 报工具清单不匹配。
- 新增**自检脚本**：`package.json` 的 `scripts` 加 `check:<name>`、插入 `check` 链、插入 `check:phase-f` 链——否则它永远不会被跑到。注意 `check` 与 `check:phase-f` 两行含相同片段，单文件定向替换须带足上下文，否则报「Found 2 occurrences」。

## 5. 规格表是单一真相源

模型/分辨率/时长/比例枚举只维护 `src/capability-registry.js` 一张表，工具 schema 枚举由表派生。新增模型时**不要**在 schema、校验集合、help 文案里各写一份——双写必然漂移。改表后跑 `check:dreamina-model-specs` 与 `check` 验证派生一致。
